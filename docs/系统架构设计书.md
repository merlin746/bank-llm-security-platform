# 链安智御 · 系统架构设计书

> **面向银行大模型生产应用的全链路安全管控平台**
> 文档版本：v1.0　|　适用代码版本：`main`
> 维护责任：段利欢（链上与链下后端）· 梅涵（网关与前端）· 史晨东（AI 算法）

## 1. 设计目标与约束

### 1.1 设计目标

| 目标 | 说明 |
| --- | --- |
| 事前管控 | 安全裁决必须发生在 LLM 生成回答**之前**，而非事后审计 |
| 毫秒级响应 | 主链路安全开销 < 10 ms，权限校验 < 2 ms |
| 确定性执行 | 权限与合规规则由链上合约裁决，结果可验证、不可单方篡改 |
| 全链路覆盖 | 输入 → 权限 → 推理 → 输出 → 定责，无保护盲区 |
| 可降级 | 任一外部依赖不可用时系统降级运行，而非整体不可用 |
| 可审计定责 | 一次请求跨四节点的处理指纹可链上比对，异常定位到具体节点 |

### 1.2 关键约束

| 约束 | 影响 | 应对 |
| --- | --- | --- |
| 银行核心链路对时延极敏感 | 不能同步写链 | 写链异步化（MQ），主链路只读缓存 |
| 链上存储与计算昂贵 | 不能把明文/大对象放链上 | 链上只存规则 ID、版本号、指纹 Hash；正文留链下 |
| 演示环境无 GPU | 模型层推理慢（3–8 s） | 规则层先行 + 模型层可选，依赖缺失自动降级 |
| 多人并行开发 | 接口易漂移 | 契约前置冻结 + 路由契约测试守护 |
| 联盟链多方参与 | 单方不能独自提交存证 | 提交者注册制 + 身份校验 |

### 1.3 质量属性

| 属性 | 目标 | 落地手段 |
| --- | --- | --- |
| 性能 | 主链路 P99 < 10 ms | Redis 预加载策略、写链异步、状态无锁读 |
| 可用性 | 依赖故障不阻断服务 | 全链路 nil 判空降级、AI 分层降级 |
| 安全 | 无越权、无明文泄露、可定责 | 链上准入 + NER 脱敏 + 指纹对账 |
| 可维护性 | 接口契约稳定、改动可验证 | 130+ 自动化测试、路由契约断言、契约变更流程 |
| 可观测性 | 每阶段耗时与裁决理由可见 | 拦截管道逐阶段回传 `latencyMs` / `message` |

### 2.2 架构分层职责

| 层 | 代码位置 | 职责 | 不该做的事 |
| --- | --- | --- | --- |
| ① 可视化层 | `frontend/src` | 数据展示、用户交互、Mock 独立演示 | 不做安全裁决（裁决权在服务端） |
| ② 网关与业务层 | `backend/` | 编排安全管道、缓存链上策略、代理 AI、异步写链 | 不承载业务语义规则（规则在链上/AI） |
| ③ 链上治理层 | `chain/contracts` | 规则固化、确定性裁决、可信存证 | 不做语义分析（不做 NLP） |
| ④ AI 风控层 | `FastAPI/` | 语义检测、脱敏、行为风险评分 | 不做权限裁决（权威在链上） |
| ⑤ 异步链路 | `backend/internal/mq` | 解耦主流程与写链、可靠投递 | 不阻塞主链路 |

> **职责边界原则**：**AI 负责"语义"，区块链负责"裁决"，网关负责"编排"。** AI 的判定是**建议性输入**，权限的最终裁决权始终在链上策略；网关只做编排与缓存，不含隐藏规则。

#### 3.1.2 五阶段拦截管道

管道在 `demo_bridge.go` 中实现，是"全链路管控"的核心体现。

```
① auth（身份认证）
      │
      ▼
② input-risk（AI 输入风险检测）  ──▶ 命中：block，短路至 ⑤
      │
      ▼
③ access-control（权限/密级/频次校验） ──▶ 不通过：block，短路至 ⑤
      │
      ▼
④ infer（LLM 推理节点）
      │
      ▼
⑤ output-sanitize（输出脱敏与合规）
```

**关键设计**

- **短路语义**：任一阶段 `block`，其后阶段标记 `skip` 且耗时为 `0`，前端据此渲染断裂的管道，直观呈现"被拦在哪一层"；
- **可观测**：每阶段回传 `latencyMs` 与 `message`（含命中原因），便于定位性能瓶颈与误判；
- **AI 调用降级**：`callAI` 调用失败时不返回错误，而是降级为规则层判定并在 `message` 中说明"AI 服务未就绪"，保证演示与业务连续性；
- **契约稳定**：阶段数量、顺序、`owner` 归属由路由契约测试守护。

#### 3.1.3 策略缓存机制

**问题**：权限裁决必须可信（在链上），但每次读链时延不可接受。

**方案**：链上存"权威版本"，链下存"已生效版本的只读副本"。

```
启动时：complianceClient.GetPolicyForCache() ──▶ Redis SET chainwise:policy:active (TTL 60s)
校验时：Redis GET（毫秒级）──▶ 命中即用
                              └─ 未命中 ──▶ 回源链上
```

**缓存键设计**（`internal/cache/redis.go`）

| 键前缀 | 用途 | 数据结构 | TTL |
| --- | --- | --- | --- |
| `chainwise:user:perm:<addr>` | 用户权限副本 | String(JSON) | 60 s |
| `chainwise:policy:active` | 生效策略与规则列表 | String(JSON) | 60 s |
| `chainwise:ratelimit:<addr>` | 滑动窗口请求计数 | String(整数) | 窗口长度 |
| `chainwise:anomaly:recent` | 近期异常事件 | List | 保留 100 条 |

**一致性权衡**：缓存是**最终一致**的。TTL 到期或策略版本变更时重新预加载；**权限的最终权威始终在链上**，缓存只用于加速读路径。

#### 3.1.4 限流设计

Redis `INCR` + 首次递增时 `EXPIRE`，实现固定窗口计数：

```
count = INCR chainwise:ratelimit:<addr>
if count == 1: EXPIRE key <windowSeconds>    // 仅首次设置过期
return count
```

> 链上 `AccessControl` 另有一套**滑动窗口**限流（时间戳数组 + 惰性清理），用于需要严格语义的场景；Redis 侧为高性能粗粒度限流。两者互补。

#### 3.1.5 降级策略

| 依赖 | 不可用时的行为 | 代码位置 |
| --- | --- | --- |
| Redis | 打警告日志，`cacheClient = nil`，所有读缓存路径跳过、直接回源链上 | `main.go` |
| RabbitMQ | 打警告日志，`mqClient = nil`，异步对账停用，主链路不受影响 | `main.go` |
| AI 服务 | 拦截管道降级为规则层判定，返回说明性 `message` | `demo_bridge.go` |
| 链上合约 | 接口桩返回演示数据，保留完整响应契约 | `internal/contract` |

> **设计原则**：安全组件的故障不应导致业务不可用，但必须**显式可见**（日志 + 响应字段），不能静默失效。

#### 3.2.2 AccessControl（分级权限准入）

**数据模型**

```solidity
enum Role      { NONE, AUDITOR, OPERATOR, MANAGER, ADMIN }
enum DataLevel { PUBLIC, INTERNAL, CONFIDENTIAL, SECRET, TOP_SECRET }

struct UserPermission { Role role; DataLevel maxAccessLevel; bool active; }
struct RateRecord     { uint256[] timestamps; }
```

**核心接口**

| 函数 | 语义 |
| --- | --- |
| `registerUser(user, role, level)` | 仅 owner；拒绝 `NONE` 角色、零地址、重复注册 |
| `deactivateUser` / `reactivateUser` | 停用/启用；停用后 `onlyActiveUser` 直接拒绝访问 |
| `updateRole` / `updateAccessLevel` | 提权与降权**立即生效** |
| `checkAccess(user, level) → (bool, string)` | 密级比较；返回拒绝原因 |
| `checkRateLimit(user) → (bool, remaining)` | 滑动窗口余量查询 |
| `recordRequest(user)` | 仅 owner；记录时间戳并**惰性清理过期记录** |

**关键实现说明**

- **滑动窗口起点必须有下溢保护**：窗口起点为 `block.timestamp - windowSeconds`，但 Solidity 0.8 对 `uint256` 下溢会 revert。当链上时间戳小于窗口长度时（本地链/测试链初始时间戳很小，或窗口配置较大），直接相减会导致 `checkRateLimit` 与 `recordRequest` 完全不可用。因此统一经 `_windowStart()` 计算，在 `block.timestamp < windowSeconds` 时退化为 `0`（语义等价于"窗口尚未滑动"）。
- **惰性清理**：`recordRequest` 在原地压缩时间戳数组并 `pop` 过期项，使存储不随调用次数无限增长。

#### 3.2.3 CompliancePolicy（合规策略执行）

**策略版本状态机**

```
proposeVersion(desc, rootHash, effectiveTimestamp)
        │  版本号自增，enacted = false
        ▼
   [待生效] ──enactVersion──▶ [已生效]  currentVersionId = versionId
        ▲                        │
        └── require(block.timestamp >= effectiveTimestamp)  // 未到生效时间不可生效
                                 └── require(!enacted)      // 不可重复生效
```

**设计意图**：策略变更不应"即时生效"，否则可在事发瞬间改规则。

**高风险操作复核状态机**

```
submitOperation(desc, reason)  ──▶  PENDING（进入待审列表）
                                       │
                    reviewOperation(opId, approved, comment)  // 仅授权审核人
                                       │
                        ┌──────────────┴──────────────┐
                        ▼                             ▼
                    APPROVED                      REJECTED
                        └───── 均从待审列表移除 ──────┘
```

**关键实现说明**

- 审核权限由 `reviewers` 映射控制，部署者为默认审核人；
- 待审列表采用 **swap-pop** 移除，复杂度 O(1)（代价是列表无序，但语义上无影响）；
- 链上仅做轻量校验（版本存在性），**内容语义合规由链下 AI 判定**，链上负责"规则确定执行"。

#### 3.2.4 NodeReconciliation（多节点对账定责）

**数据模型**

```solidity
enum NodeType { ACCESS, RAG, INFERENCE, DATA_WAREHOUSE }

struct RequestRecord {
    string      requestId;
    bytes32[4]  nodeHashes;    // 四节点指纹
    address[4]  submitters;    // 各节点提交者
    uint256[4]  timestamps;
    bool[4]     submitted;     // 显式已提交标志位
    uint8       submitCount;
    bool        reconciled;
    uint256     reconciledAt;
}
```

**对账流程**

```
submitNodeHash(requestId, nodeType, hash)   ← onlyRegisteredSubmitter
        │
        ├─ 首次提交：初始化 RequestRecord，recordCount++
        ├─ require(!reconciled)                       // 已对账不可再提交
        ├─ require(!submitted[nodeType])              // 显式标志位判重
        ├─ 记录指纹/提交者/时间戳，submitCount++
        │
        └─ submitCount == 4 ──▶ reconcile() 自动触发
                                   │
                                   ├─ 统计众数 → consensusHash（多数派）
                                   ├─ 一致（4/4）→ consistent = true
                                   └─ 不一致 → 标记离群节点，逐节点 emit AnomalyDetected
```

**两处关键实现说明（均为缺陷修复）**

1. **提交者身份校验必须真正生效**。原实现中修饰器内声明了局部变量 `bool registered;`（恒为 `false`），且带有占位事件 `emit ... // placeholder`，并且**该修饰器未被任何函数使用**——任何地址都能提交，链上存证完全失去可信性。
   现实现引入反向索引 `mapping(address => bool) public isRegisteredSubmitter`，对照正向表 `registeredSubmitters` 保持双向一致（注册/移除/改绑均同步维护），修饰器改为 O(1) 校验 `msg.sender`，并实际挂载到 `submitNodeHash` 上。部署者在构造函数中注册为初始可信提交者，保证部署后立即可用。

2. **判重必须用显式标志位，而非"指纹是否为零"**。原实现以 `nodeHashes[idx] == bytes32(0)` 判定重复提交。但 **`bytes32(0)` 是合法指纹**（例如某节点在该请求上的载荷为空时），合法提交会被误判为"尚未提交"，使 `submitCount` 与真实状态脱节。现实现改用 `bool[4] submitted` 显式标志位。

**众数统计的确定性语义**

统计众数时使用严格大于比较（`hashCounts[i] > maxCount`），因此出现平局时**先提交的指纹成为参考值**。例如 2-2 平局：判为 `consistent = false`，参考值取先提交的那一组，另 2 个节点被判为离群。该行为是确定性的——结果只取决于提交顺序，不依赖其他因素。

#### 3.2.5 节点指纹计算规范

链上只做**比对**，不计算；指纹由链下计算后提交。因此算法必须链上链下严格一致：

```
nodeHash = SHA-256( "chainwise.node-hash.v1" || 0x00 || requestID || 0x00
                    || uint32(nodeType) 大端 || 0x00 || payload )
```

**为什么不用简单拼接**：若用可打印字符（如 `"|"`）拼接字段，`("a|b", "c")` 与 `("a", "b|c")` 会产生相同输入串，不同逻辑内容得出相同指纹，对账即失去意义。使用 `0x00` 作为分隔符可消除歧义；`nodeType` 用定长大端整数编码，避免 `1` 与 `01` 的歧义。

**为什么指纹不能恒为零**：若指纹算法实现有误（例如返回常量），四节点永远"一致"，对账形同虚设。因此 `CalculateNodeHash` 的测试同时断言"与标准库 SHA-256 一致"与"不得为全零"。

### 3.3 AI 风控层

#### 3.3.1 模块构成

| 模块 | 算法 | 输出 |
| --- | --- | --- |
| `PromptDetector` | 规则层（6 条正则）+ 模型层（Qwen2-1.5B + LoRA + 二分类头） | `is_attack` / `confidence` / `reason` / `layer` |
| `Desensitizer` | 正则层 + SpaCy 中文 NER + 关键词合规评分 | `desensitized_text` / `detected_entities` / `compliance` |
| `RiskScorer` | IsolationForest（7 维行为特征） | `score` / `is_anomaly` / `level` / `features` |

#### 3.3.2 分层降级设计

**这是 AI 层最重要的架构决策**：任一层依赖缺失都不应导致服务不可用。

| 缺失依赖 | 行为 |
| --- | --- |
| `torch` / `transformers` / `peft` 未安装 | 导入失败被捕获，`HF_AVAILABLE = false`，仅规则层可用 |
| LoRA adapter 或分类头文件缺失 | 加载异常被捕获，打印警告，`model_ready = false`，仅规则层可用 |
| `spacy` 未安装或 `zh_core_web_sm` 未下载 | 跳过 NER 层，保留正则与合规检测 |
| 风险模型 `.joblib` 缺失 | 使用未训练的 IsolationForest（可运行但精度受限） |

**规则层的价值**：不仅用于降级，更是**一级检测器**——正则命中可毫秒级返回且给出可解释原因，无需等待模型推理。

#### 3.3.3 脱敏去重策略

正则规则存在包含关系（银行号 16–19 位数字会包含手机号 11 位），因此：

1. 收集所有正则命中实体；
2. **按 span 长度降序排序**（长实体优先）；
3. 逐个纳入，**丢弃与已选实体重叠者**；
4. 按 span 起始位置**从后往前替换**，避免替换导致后续偏移错位。

结果：身份证号不会被手机号规则截断，长实体优先获胜。

#### 3.3.4 风险特征设计

| 特征 | 攻击/异常信号 |
| --- | --- |
| `call_count_1h` / `call_count_24h` | 高频调用（自动化探测） |
| `night_rate` | 异常时段活动 |
| `avg_interval` | 间隔过短（脚本化） |
| `unique_ip_count` | 多 IP 跳变（账号共享/盗用） |

## 4. 关键流程时序

### 4.1 一次受保护请求（正常放行）

```
用户 ──▶ 前端 ──▶ 网关
                  │
                  ├─ ① 身份认证（本地）────────────────────── pass, 1ms
                  ├─ ② POST /api/prompt/detect（AI 服务）─── pass, 12ms
                  ├─ ③ Redis GET 策略 + 密级/频次校验 ────── pass, 2ms
                  ├─ ④ LLM/RAG 推理 ────────────────────── pass, 46ms
                  ├─ ⑤ POST /api/output/desensitize ────── 脱敏+合规评分, 9ms
                  │
                  └──▶ 响应 { verdict: pass, totalLatencyMs, stages[5] }
```

### 4.2 一次被拦截请求（短路）

```
用户 ──▶ 前端 ──▶ 网关
                  │
                  ├─ ① 身份认证 ──────────────────────── pass
                  ├─ ② AI 输入检测 ───────────────────── block ← 命中越狱意图
                  ├─ ③ 权限/密级校验 ─────────────────── skip（未执行）
                  ├─ ④ 推理 ──────────────────────────── skip（未进入推理）
                  └─ ⑤ 输出脱敏 ──────────────────────── skip
                  │
                  └──▶ 响应 { verdict: block, stages[2].extra.riskType: "jailbreak" }
```

### 4.3 异步四节点对账

```
四节点链下服务
    │ 各自计算 nodeHash = SHA256(domain || requestId || nodeType || payload)
    ▼
POST 消息 ──▶ RabbitMQ（exchange: chainwise.reconciliation, queue: node.hash.submit）
                    │ 持久化投递
                    ▼
              网关 MQ 消费者
                    │ 反序列化 HashSubmitMessage
                    ▼
              NodeReconciliation.submitNodeHash(...)
                    │
                    ├─ 未满 4 个 ──▶ Ack，等待其余节点
                    └─ 第 4 个 ──▶ 自动 reconcile()
                                      │
                                      ├─ consistent ──▶ 仅存证
                                      └─ 不一致 ──▶ GetReconciliationResult
                                                        │
                                                        └─ PushAnomaly → Redis List
                                                                              │
                                                                              └─▶ 大屏展示
                    │
              处理成功 ──▶ Ack
              处理失败 ──▶ Nack(requeue=true) 重入队
```

### 4.4 策略版本更新

```
owner: proposeVersion(desc, rootHash, effectiveTimestamp)  ──▶ 待生效版本
                                                                    │
        （等待 block.timestamp >= effectiveTimestamp）                │
                                                                    ▼
owner: enactVersion(versionId) ──▶ currentVersionId 更新
                                        │
                                        ▼
                        链下缓存 TTL 到期后重新预加载
                                        │
                                        ▼
                        Redis chainwise:policy:active 更新
                                        │
                                        ▼
                        后续权限校验使用新策略（毫秒级）
```

### 5.1 链上数据结构

| 合约 | 结构 | 关键字段 |
| --- | --- | --- |
| AccessControl | `UserPermission` | `role`, `maxAccessLevel`, `active` |
| AccessControl | `RateRecord` | `timestamps[]`（滑动窗口） |

| CompliancePolicy | `HighRiskOperation` | `operationId`, `operator`, `status`, `reviewer`, `reviewComment` |

| NodeReconciliation | `ReconciliationResult` | `consistent`, `consensusHash`, `anomalousNodes[]` |

**链上存储原则**：只存**规则标识、版本号、指纹 Hash、状态枚举**；明文内容、脱敏正文、用户行为日志一律留链下（合规要求 + 成本约束）。

### 5.2 Redis 键设计

见 [3.1.3](#313-策略缓存机制)。补充说明：

- 异常列表使用 `LPUSH` + `LTRIM 0 99` 保留最近 100 条，避免无界增长；
- 限流键仅在首次 `INCR` 时设置 `EXPIRE`，避免每次调用重置过期时间（否则窗口永不结束）。

### 5.3 MQ 消息结构

**HashSubmitMessage**（`node.hash.submit`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | string | 请求 ID |
| `node_type` | int | 节点类型序号 0–3 |
| `node_hash` | string | 节点指纹 |
| `submitter` | string | 提交者地址 |
| `timestamp` | int64 | 提交时间 |

**ReconSummaryMessage**（`recon.summary`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | string | 请求 ID |
| `consistent` | bool | 是否一致 |
| `consensus_hash` | string | 共识指纹 |
| `anomaly_nodes` | int[] | 离群节点序号 |

**可靠性设计**：交换机与队列均 `durable`，消息 `DeliveryMode: Persistent`，消费端**手动 Ack**、失败 `Nack(requeue=true)`。

## 6. 横切关注点

### 6.1 降级与容错

| 组件 | 故障表现 | 降级行为 | 可见性 |
| --- | --- | --- | --- |
| Redis | 连接超时（3 s） | 无缓存运行，直读链上 | 启动日志 + `/health` 的 `redis` 字段 |
| RabbitMQ | 拨号失败 | 停止异步对账 | 启动日志 |
| AI 服务 | HTTP 错误/超时（15 s） | 规则层判定 | 阶段 `message` 明确说明 |
| AI 模型产物 | 文件缺失 | 仅规则层 | 加载警告日志 |
| SpaCy 模型 | 未下载 | 跳过 NER | 警告日志 |
| 链上合约 | 未接入 | 接口桩返回演示数据 | 代码 `TODO` + 开题报告状态说明 |

**原则**：降级必须**显式可见**，绝不静默失效——静默失败的安全组件比没有安全组件更危险。

### 6.2 安全设计

| 层面 | 措施 |
| --- | --- |
| 身份 | 请求携带 Bearer 令牌；401 自动跳转登录（真实认证待接入链上签名） |
| 授权 | 角色 × 密级二维准入；链上裁决为权威 |
| 频次 | Redis 固定窗口（高性能）+ 链上滑动窗口（严格语义） |
| 数据 | 输出侧正则 + NER 双层脱敏；响应中永不返回密码字段 |
| 与链交互 | 提交者注册制 + `onlyRegisteredSubmitter` 校验；`onlyOwner` 保护管理接口 |
| 重放/重复 | 链上 `submitted[4]` 显式判重；`reconciled` 标志防止重复对账 |
| 审计 | 四节点指纹链上比对；异常节点精确定位 |
| 密钥 | `.gitignore` 禁止提交 `.env` / `*.pem` / `*.key` / `*.p12` |

### 6.3 性能设计

| 手段 | 效果 |
| --- | --- |
| 策略 Redis 预加载 | 权限校验从"读链"降为"读内存/Redis"，达到毫秒级 |
| 写链异步化 | 主链路不承担链上共识时延 |
| 管道短路 | 拦截后不再执行后续阶段（省去推理与脱敏开销） |
| 规则层前置 | 高频攻击样本毫秒级判定，不进入模型推理 |
| 惰性清理 | 限流时间戳数组按需压缩，存储与遍历成本有界 |

### 6.4 可观测性

| 手段 | 内容 |
| --- | --- |
| 分阶段耗时 | 拦截管道每阶段回传 `latencyMs` |
| 裁决理由 | 每阶段回传 `message`（含命中规则/拒绝原因） |
| 结构化日志 | 启动、降级、MQ 处理、对账完成均有 `[INFO]` / `[WARN]` / `[MQ]` 前缀日志 |
| 健康检查 | `/api/v1/health` 暴露服务与 Redis 状态 |
| 业务指标 | 态势大屏展示请求量、拦截量、拦截率、高风险用户数 |

### 6.5 错误处理约定

| 层 | 约定 |
| --- | --- |
| 网关 Handler | 统一 `model.Error(code, msg)` 返回，不向客户端暴露内部错误细节 |
| AI 代理 | 上游不可达返回 `502`；非 JSON 响应按原文透传 |
| MQ 消费者 | 处理失败 `Nack(requeue=true)` + 错误日志；成功 `Ack` |
| 合约 | `require` + 语义化错误信息（如 `"NodeReconciliation: submitter not registered"`），便于链上定位 |

## 8. 关键技术决策

| 决策 | 选择 | 备选 | 理由 |
| --- | --- | --- | --- |
| 链上 vs 链下裁决 | 链上固化规则，链下缓存加速 | 全链上 / 全链下 | 全链上时延不可接受；全链下失去可信性 |
| 写链同步 vs 异步 | **异步（MQ）** | 同步写链 | 链上共识时延会直接转化为业务时延，且链拥堵会导致业务不可用 |
| 注入检测架构 | **规则层 + 模型层分层** | 纯规则 / 纯模型 | 纯规则易绕过；纯模型慢且不可解释；分层兼顾速度、准确率与可解释性 |
| 指纹分隔符 | **`0x00` 不可打印字符** | `"|"` 等可打印字符 | 可打印分隔符会因字段内容含分隔符而产生歧义 |
| 链上判重依据 | **显式 `bool[4] submitted`** | 指纹是否为 0 | `bytes32(0)` 是合法指纹，用零值判重会误判 |
| 提交者校验 | **地址反向索引 O(1)** | 遍历正向表 | 遍历成本随节点数增长；反向索引可 O(1) 校验且双向一致 |
| 前端数据源 | **Mock 开关 + 契约一致** | 强依赖后端 | 前端可独立演示，同时联调时行为一致 |
| 降级策略 | **全链路 nil 判空降级** | 依赖不可用即启动失败 | 安全组件故障不应导致业务整体不可用 |

### 9.2 契约守护机制

由于前端、Go 后端、AI 服务三方并行开发，接口漂移是本项目最大的协作风险。为此建立三道防线：

1. **路由契约测试**（`router_contract_test.go`）：把前端实际调用的每条路由写入测试表，缺失即失败；

3. **管道契约测试**：断言 `stages[]` 的阶段数量、顺序、`status` 合法性与 `totalLatencyMs` 一致性。

### 9.3 合约测试无需外部依赖

Foundry 测试**不依赖 forge-std**：自定义最小断言基类（`ChainWiseTestBase`）并只声明用到的 cheatcode 子集。这样在没有外网的环境下 `forge test` 依然可运行，避免因 `forge install` 失败而无法回归。
