## 1. 项目概述

### 1.1 项目名称

**链安智御（ChainWise Guard）** —— 面向银行大模型生产应用的全链路安全管控平台。

### 1.2 一句话定位

不是给大模型叠加更多"补丁式"内容过滤，而是为大模型在银行核心业务中的每一次调用建立**事前硬拦截、事中语义脱敏、事后链上定责**的全链路安全管控闭环。

### 1.3 项目组成

| 层次 | 技术选型 | 职责 |
| --- | --- | --- |
| 链上治理层 | FISCO BCOS v3.x · Solidity ^0.8.0 | 权限准入、合规策略、多节点对账定责 |
| 链下网关层 | Go 1.21 · Gin · go-redis · RabbitMQ | 拦截管道、策略缓存、异步上链 |
| AI 风控层 | Python · FastAPI · PyTorch · Qwen2 | 注入检测、输出脱敏、行为风险评分 |
| 可视化层 | Vue 3 · Element Plus · ECharts · Pinia | 态势大屏、攻防测试、审计溯源 |

## 2. 研究背景与痛点

### 2.1 行业背景

工商银行持续推进"数字工行"战略并率先发布千亿级金融大模型"工银智涌"，标志着大模型已从试点走向银行核心业务生产环境。但**大模型在银行落地时，安全合规始终是第一道门槛**。

### 2.2 三类核心痛点

**痛点一：注入攻击激增，传统防护失效**

- 2026 年上半年，大模型提示词注入、数据投毒、模型窃取等攻击同比增长 **210%**，其中 **34%** 可绕过传统 WAF 与关键词内容过滤。
- *来源：CNCERT 2026 上半年 AI 安全态势报告*
- 根本原因：提示词注入是**语义层**攻击，而 WAF 与关键词过滤工作在**字符串层**。攻击者只需改写措辞（如把"忽略之前的指令"改为"请忘掉你收到的最初设定"）即可绕过规则。

**痛点二：敏感数据经大模型链路外泄**

- 生成式 AI 相关数据政策违规事件中，**59%** 涉及受监管金融数据。
- *来源：Netskope Threat Labs 2026 年度报告*
- 银行大模型链路上，客户姓名、身份证号、银行卡号、账户余额、征信明细等会同时流经访问网关、RAG 检索、推理、数仓四个节点，任一节点输出未脱敏即构成泄露。

**痛点三：合规监管划定硬红线**

- 国家金融监督管理总局（2026-06）明确：**姓名、身份证号、手机号、银行卡号等个人信息不得用于生成式 AI 模型的训练与优化**。
- 合规要求不仅是"别泄露"，还要求**可审计、可举证、可定责**——而传统日志系统由单方运维、事后可被篡改，无法作为可信证据。

### 2.3 核心矛盾

> **安全合规的速度，追不上大模型业务落地的速度。**

银行面临两难：收紧管控则业务部门无法用大模型提效；放开使用则合规风险不可控。二者之间的缺口，正是本项目要填补的空间。

## 3. 国内外研究现状

| 方向 | 现有主流做法 | 局限 |
| --- | --- | --- |
| 输入安全 | 关键词黑名单、WAF、正则规则 | 字符串层匹配，易被语义改写绕过 |
| 输入安全（进阶） | 单向安全大模型/分类器判别 | 单点模型，存在误判与对抗样本风险，且结果不可验证 |
| 输出安全 | DLP、正则脱敏 | 难以覆盖非结构化自由文本，且无合规策略统一裁决 |
| 权限管控 | 集中式 IAM / RBAC | 单点信任，授权变更与审计记录由运维方单方掌握 |
| 审计溯源 | 集中式日志、ELK | 日志可被有权限者修改，缺乏多方共识与可信存证 |
| 链上存证 | 区块链存证哈希 | 多用于文件存证，未与实时权限校验及策略执行结合 |

**结论**：现有方案要么停留在字符串层（易绕过），要么是单点集中式（不可信），要么只覆盖单一环节（不成闭环）。**"AI 语义能力"与"区块链确定性执行"尚未被系统性地组合成一条完整链路。**

## 4. 项目目标

### 4.1 总体目标

构建一套可运行、可演示、可审计的全链路安全管控平台，实现：

1. 大模型回答生成**之前**完成注入识别与权限/密级/频次硬拦截；
2. 生成结果输出**前**完成敏感信息脱敏与合规话术评分；
3. 一次请求跨四个节点的处理指纹在链上比对，**自动定位异常节点**并留痕。

### 4.2 可量化指标

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| 主链路安全响应 | < 10 ms | 策略经 Redis 预加载，权限校验 < 2 ms |
| 注入检测规则层命中 | < 10 ms | 正则规则层，覆盖高频攻击样本 |
| 注入检测模型层推理 | 200–500 ms | NVIDIA GPU + fp16/4-bit 量化（CPU 环境 3–8 s） |
| 脱敏准确率 | 手机号/身份证/银行卡号 100% 覆盖 | 正则 + 中文 NER 双层，长实体优先去重 |
| 上链时延 | 不阻塞主流程 | MQ 异步写链，四节点齐备后自动触发对账 |
| 异常定位粒度 | 单节点级 | 输出具体离群节点类型（访问/RAG/推理/数仓） |

## 5. 主要研究内容与关键技术

### 5.1 研究内容

**内容一：链上分级权限准入与合规策略执行**

- 设计角色（AUDITOR/OPERATOR/MANAGER/ADMIN）与数据密级（PUBLIC→TOP_SECRET）双维度准入模型；
- 实现滑动时间窗口限流，防止高频滥用与自动化探测；
- 实现策略版本状态机：提议（propose）→ 生效（enact），版本生效需满足生效时间，避免策略被即时篡改；
- 实现高风险操作人工复核状态机（PENDING → APPROVED/REJECTED）。

**内容二：链下毫秒级策略缓存与拦截管道**

- 启动时将链上生效策略预加载进 Redis（带 TTL 与预热），将链上确定性执行的"信任"与链下的"速度"解耦；
- 构建五阶段拦截管道：身份认证 → AI 输入风险检测 → 权限/密级校验 → LLM 推理 → 输出脱敏与合规；
- 任一阶段拦截即短路后续阶段，并向前端完整回传每阶段耗时与裁决理由。

**内容三：AI 语义防护（检测 / 脱敏 / 风控）**

- 注入检测采用**规则层 + 模型层**双级：规则层保证毫秒级与可解释，模型层（Qwen2-1.5B + LoRA + 二分类头）覆盖语义变体；
- 输出脱敏采用**正则 + 中文 NER** 双层，正则层按实体长度降序去重（长实体优先，避免身份证被手机号规则截断）；
- 行为风控采用孤立森林（Isolation Forest），基于 7 维行为特征输出 0–100 动态风险分。

**内容四：四节点异步对账与精准定责**

- 访问 / RAG / 推理 / 数仓四节点各自计算处理指纹，经 MQ 异步提交链上；
- 四节点齐备后自动触发对账，取多数派为共识 Hash，标记偏离节点；
- 全流程与主业务响应解耦，避免"写链拖慢请求"。

**内容五：全链路可视化与攻防对抗演示**

- 安全态势大屏（KPI、拦截趋势、风险分布、高风险用户榜）；
- 模拟攻防测试页（Prompt 注入 / 越权访问双模式，逐阶段展示拦截管道）；
- 审计溯源页（四节点 Hash 拓扑图，异常节点红色标记 + 告警日志）。

### 5.2 关键技术难点与解决思路

**难点一：语义级注入检测的准确率与响应速度难以兼顾**

- *难点*：纯模型方案准但慢（CPU 上秒级），纯规则方案快但易被绕过。
- *思路*：分层降级。规则层先做毫秒级初筛并给出**可解释的命中原因**；未命中再交由模型层做语义判别。模型或依赖缺失时自动降级为仅规则层，保证服务始终可用而非整体不可用。

**难点二：链上策略的确定性与链下毫秒级响应之间的张力**

- *难点*：每次权限校验都读链，时延不可接受；只读本地缓存，则策略变更无法即时生效、且失去可信性。
- *思路*：**缓存 + 版本化 + TTL**。策略以带版本号和生效时间的结构固化在链上，链下只缓存"已生效版本"，TTL 到期或版本变更时重新预加载。既保住毫秒级响应，又确保"谁能访问什么"最终由链上裁决。

**难点三：四节点指纹的对账确定性**

- *难点*：Hash 计算的字段拼接若存在歧义，不同节点对同一逻辑内容可能算出不同指纹，造成误报；若指纹恒为常量，则对账彻底失效。
- *思路*：定义**带域分隔前缀的结构化编码**——固定域前缀 + `0x00` 字段分隔符 + 节点类型以大端 4 字节整数参与编码。用不可打印分隔符替代 `"|"` 等可打印字符，消除"字段内容本身含分隔符"导致的歧义；并为此编写针对性的歧义回归测试。

**难点四：异步上链的可靠性与幂等**

- *难点*：MQ 消息可能重复或失败，重复提交会破坏对账状态。
- *思路*：链上用**显式已提交标志位**（而非"Hash 是否为零"）判定重复提交，避免合法零值被误判；合约端校验提交者身份；MQ 侧采用手动 Ack + 失败重入队。

## 6. 技术路线与系统架构

### 6.1 总体架构

```
                    ┌──────────────────────────────────────────┐
   用户请求 ───────▶ │            Go 安全网关（:8080）            │
   业务调用          │  Gin · Redis 策略缓存 · 拦截管道            │
                    └───────────────┬──────────────────────────┘
                                    │
                ┌───────────────────┼───────────────────┐
                ▼                   ▼                   ▼
        ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
        │ AI 输入风险检测 │   │ 权限/密级校验  │   │  LLM / RAG    │
        │ FastAPI·Qwen2 │   │  Redis + 链上  │   │  推理节点      │
        └───────────────┘   └───────────────┘   └───────┬───────┘
                                                        ▼
                                              ┌───────────────────┐
                                              │ 输出脱敏与合规评分  │
                                              │  NER + 正则 + 策略 │
                                              └─────────┬─────────┘
                                                        │
   ┌────────────────────────────────────────────────────┼──────────────────┐
   │ 异步链路（不阻塞主流程）                              │                  │
   │   四节点 Hash ──▶ RabbitMQ ──▶ 链上对账 ──▶ 异常事件 ──▶ Redis ──▶ 大屏  │
   └───────────────────────────────────────────────────────────────────────┘
```

### 6.2 请求执行流程

1. **身份认证**：校验令牌与会话有效性；
2. **AI 输入风险检测**：规则层 → 模型层，识别注入/越狱/越权意图；命中即拦截（后续阶段标记 skip）；
3. **权限 / 密级 / 频次校验**：读 Redis 中链上生效策略，校验角色-密级匹配与滑动窗口频次；
4. **LLM / RAG 推理**：通过校验后进入推理；
5. **输出脱敏与合规**：正则 + NER 打码，违规理财话术合规评分；
6. **异步对账**：四节点指纹经 MQ 聚合上链，触发对账并按需告警。

### 6.3 三大核心创新

| 创新 | 内容 | 支撑技术 |
| --- | --- | --- |
| **创新一**<br>变「事后日志」为「事前规则硬拦截」 | 数据密级与合规策略固化于链上，结合缓存预加载，在回答生成**之前**完成毫秒级访问管控 | Solidity 三合约 + Redis 预加载 |
| **创新二**<br>无感高并发的「异步四节点分布式对账」 | 四节点 Hash 链上比对，主流程与写链解耦，高并发下仍可精准定责 | RabbitMQ + NodeReconciliation 合约 |
| **创新三**<br>AI 语义防护 × 区块链确定性执行 | AI 解决非结构化语言的语义安全与脱敏，区块链保证规则确定执行与多方信任，形成双重防线 | Qwen2 / NER / 孤立森林 + FISCO BCOS |

### 6.4 关键工程设计

**写链异步化，不卡主流程**

- 传统做法：写链交易同步进入请求管道 → 时延高，且链上拥堵会直接导致业务不可用；
- 本平台：主链路只做"读"（读缓存中的已生效策略），"写"（四节点指纹上链）全部走 MQ 异步，主业务响应控制在 10 ms 级，兼顾高并发与合规存证。

## 7. 创新点总结

1. **事前性**：安全管控点前移到回答生成之前，而非事后审计日志。
2. **确定性**：策略执行由链上合约完成，规则公开、执行结果可验证，不依赖运维方单方声明。
3. **全链路**：覆盖"输入—权限—推理—输出—定责"完整链路，而非单点防护。
4. **无感化**：异步对账使合规能力不对业务时延产生可感知影响。
5. **可降级**：AI 模型、Redis、MQ 任一依赖不可用时，系统降级运行而非整体崩溃。

## 8. 可行性分析

### 8.1 技术可行性

- 四层技术栈均为成熟开源方案（FISCO BCOS / Go·Gin / FastAPI / Vue 3），无自研底层依赖；
- 三大合约已完整实现并通过 **73 项 Foundry 单元测试**（覆盖权限准入、策略版本状态机、高风险操作复核、四节点对账与离群识别、提交者身份校验、限流窗口滑动等）；
- Go 后端已通过 **82 项单元测试**，覆盖路由契约、CRUD 边界、AI 降级、分片统计与审计接口；
- AI 侧三项能力均有可运行的降级实现（模型缺失时退化为规则层/正则层），保证在无 GPU 环境下也能演示完整链路。

### 8.2 经济可行性

- 全栈开源，无商业授权费用；
- 演示环境可运行于普通开发机（CPU 推理）；生产环境仅需一台 NVIDIA GPU 服务器承载模型层；
- 链上采用联盟链，节点由银行内部或同业联盟部署，无需公链 Gas 成本。

### 8.3 操作可行性

- 前端提供完整可视化界面，风控人员无需接触底层即可完成日常审核；
- 高风险操作走"人工复核状态机"，符合银行现有双人复核的业务习惯。

### 8.4 风险分析与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 无 GPU，模型层推理慢 | 演示体验差 | 分层降级；演示优先使用规则层可命中样本，实现毫秒级响应 |
| 合约调用尚未接入真实链 | 无法端到端演示链上能力 | 当前以接口桩 + 内存数据保障前端联调；接口边界已固化，替换为 Go-SDK 调用不影响上层 |
| 训练数据为小规模标注集 | 模型泛化能力有限 | 训练脚本与数据管线已就绪，后续替换真实业务日志即可增量训练 |
| 策略缓存与链上状态不一致 | 越权风险 | 缓存带 TTL + 版本号；版本变更触发重新预加载；权限最终以链上为准 |
